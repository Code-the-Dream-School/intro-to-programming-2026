# Week 11 Answer Key — Final Project

## Setup & submission

- **This is a capstone submission week, not numbered questions.** There is no new coding assignment — students finish two projects they have been building since ~Week 5: the **portfolio page** (`index.html`) and the **Open API page** (`openapi.html`). Work runs in the **browser** (open the HTML files, or use the **Live Server** VS Code extension). Grade against the two rubric-driven deliverables below.
- **Git workflow (finish + consolidate) — taken from the assignment; verify each step happened:**
  1. **Finish the code** on both the portfolio and Open API pages against their rubrics.
  2. **Merge all open pull requests into `main`** on GitHub (Pull Requests tab → open each PR → **Merge pull request** → confirm). Nothing should be left on an unmerged `lesson-N` branch.
  3. Locally: `git checkout main` → `git pull origin main` so `main` reflects every merged branch.
  4. Confirm the deployed/served site renders from `main` — this is what graders and the demo will show.
- **Submission (non-coding):** click the submission button and paste the **repository URL** (`https://github.com/yourUsername/yourRepositoryName`) into the project link field. Note this is the **repo URL**, not a PR URL — the opposite of prior weeks. Do not grade this as a task.
- **Demo video (non-coding — do not grade):** a 3–5 min recording that scrolls the portfolio, demonstrates the message form (add + edit/delete an entry), switches to the Open API page, shows both endpoints loading with navigation between them, switches back, then reflects on the hardest and most enjoyable parts. Uploaded to YouTube as **Unlisted**. Confirm it exists and the link was submitted; do not grade its content.
- **Course assessment (non-coding — do not grade):** a separate assessment (link via Slack) is required to graduate. Not part of the code review.
- **Rubrics:** the [Portfolio Rubric](https://github.com/Code-the-Dream-School/intro-to-programming-2026/wiki/Portfolio-Rubric) and [Open API Rubric](https://github.com/Code-the-Dream-School/intro-to-programming-2026/wiki/Open-API-Rubric) are external wiki pages. The requirements evaluated below are drawn from the assignment/lesson description of those rubrics — treat the live wiki as the source of truth if it differs.

## Portfolio page (`index.html`)

The portfolio is the accumulation of Weeks 5–10 work. Evaluate the discrete rubric requirements below; most are **Objective** because they have one correct mechanism (dynamic year, looped skills, working form) even though the styled content is personal.

### Required sections present · Subjective

- Correct answers include the standard portfolio sections: **About**, **Experience**, **Skills**, **Projects**, and a **"Leave a Message"** form section. Content is personal — check that each section exists and is populated, not the specific wording.
- The page should be a coherent, styled single page (CSS applied, readable layout, navigation to the sections). A weak answer leaves default unstyled HTML or is missing whole sections.
- Reciprocal link present: the portfolio must link **out to the Open API page**. See the reciprocal-links task below.

### Dynamic footer copyright year · Objective

```js
const footer = document.querySelector("footer");
const today = new Date();
const copyright = document.createElement("p");
copyright.innerHTML = "&copy; Jane Doe " + today.getFullYear(); // © Jane Doe 2026
footer.appendChild(copyright);
```
Expected result: a footer paragraph with the student's name and the **current year**. The year must come from `getFullYear()`, **not** a hardcoded `2026`. Name value is personal — check the mechanism, not the literal.

**Mentor note:** A hardcoded year renders identically today, so it "looks right" but fails the rubric. Confirm the year is generated by JS — the quickest check is that no literal year appears in the HTML/JS for the footer.

### Skills rendered from an array via a loop · Objective

```js
const skills = ["JavaScript", "HTML", "CSS", "Git", "React"];
const skillsList = document.querySelector("#skills ul");

for (let i = 0; i < skills.length; i++) {
  const li = document.createElement("li");
  li.textContent = skills[i];
  skillsList.appendChild(li);
}
```
Expected result: one `<li>` per array element under the Skills section. Array contents are personal — check the **pattern** (array → loop → create `<li>` → append), not the specific skills. The `<li>` elements must be **generated by JavaScript**, not written by hand in the HTML.

**Mentor note:** Hardcoded `<li>`s in the HTML are the common failure here — same visual result, but it does not satisfy the "rendered from a JS array via a loop" rubric line.

### "Leave a Message" form — validate, display, remove · Objective

```js
const form = document.querySelector("#message-form");
const messageList = document.querySelector("#messages");

form.addEventListener("submit", (event) => {
  event.preventDefault();

  const name = form.elements["name"].value.trim();
  const message = form.elements["message"].value.trim();
  if (!name || !message) return; // validation: don't add empty entries

  const li = document.createElement("li");
  li.textContent = `${name}: ${message}`;

  const removeBtn = document.createElement("button");
  removeBtn.textContent = "Remove";
  removeBtn.addEventListener("click", () => li.remove());

  li.appendChild(removeBtn);
  messageList.appendChild(li);
  form.reset();
});
```
Expected behavior, all three required:
- **Validate** — empty name or message is rejected (no blank entry added).
- **Display** — a valid submission appends a visible entry to the message list.
- **Remove** — each entry has a working delete/remove control that takes it off the page.
An edit control is a plus (the demo mentions "edit or delete"), but remove is the minimum.

**Mentor note:** Two frequent gaps — (1) missing `event.preventDefault()`, so the form submits and the page reloads, wiping the list; (2) form displays but has **no remove button**, which fails the rubric even though adding works.

### GitHub repos fetched from the API and displayed · Objective

```js
async function loadRepos() {
  try {
    const response = await fetch("https://api.github.com/users/USERNAME/repos");
    if (!response.ok) throw new Error(`Request failed: ${response.status}`);
    const repos = await response.json();

    const list = document.querySelector("#projects ul");
    repos.forEach((repo) => {
      const li = document.createElement("li");
      const link = document.createElement("a");
      link.href = repo.html_url;
      link.textContent = repo.name;
      li.appendChild(link);
      list.appendChild(li);
    });
  } catch (error) {
    console.error(error);
    // show a fallback message to the user
  }
}
loadRepos();
```
Expected result: the student's public GitHub repos are fetched at runtime and rendered (typically as links). Check that the data is **fetched from the API**, not a hardcoded list, and that the response is awaited/handled asynchronously.

**Mentor note:** The GitHub REST API rate-limits unauthenticated requests (60/hour per IP). A student whose page "sometimes shows nothing" may be rate-limited, not broken — check the console/network tab for a 403 before flagging the code.

## Open API page (`openapi.html`)

A **separate** page with its own CSS/JS files. This is where the most common gaps appear — verify each item renders live, not just that the code exists.

### Two distinct GET requests to two different endpoints · Objective

```js
async function getFrom(url, render) {
  try {
    const response = await fetch(url);
    if (!response.ok) throw new Error(`Request failed: ${response.status}`);
    const data = await response.json();
    render(data);
  } catch (error) {
    showError(error); // see error-handling task
  }
}

getFrom("https://api.example.com/resource-a", renderA);
getFrom("https://api.example.com/resource-b", renderB);
```
Requirement: **two distinct GET requests to two different endpoints**, each rendering its own view of data. Any public API is acceptable; the two endpoints must return different resources.

**Mentor note:** This is the single most common gap — students ship **one** working fetch and stop. Confirm both endpoints actually render data on the page before signing off; do not accept two `fetch` calls in the code if only one view populates.

### Navigation between the two data views · Objective

```js
const viewA = document.querySelector("#view-a");
const viewB = document.querySelector("#view-b");

document.querySelector("#show-a").addEventListener("click", () => {
  viewA.hidden = false;
  viewB.hidden = true;
});
document.querySelector("#show-b").addEventListener("click", () => {
  viewA.hidden = true;
  viewB.hidden = false;
});
```
Requirement: the user can **toggle between the two data views** (buttons, tabs, or links that show one endpoint's data at a time, or otherwise switch context). Both views existing on the page with no way to switch does **not** satisfy this.

### Error handling for failed fetches · Objective

```js
function showError(error) {
  const banner = document.querySelector("#error");
  banner.textContent = "Sorry, we couldn't load that data. Please try again.";
  banner.hidden = false;
  console.error(error);
}
```
Requirement: a failed fetch (bad response / network error) shows the **user** a message, not just a silent console log. The `catch` block (and an `!response.ok` check) must lead to visible feedback.

**Mentor note:** This rubric line is easy to skip because it never triggers on the happy path. To verify, have the student temporarily break the URL (or throw in `render`) and confirm a message appears on the page — an empty `catch {}` or a console-only log does not meet the requirement.

### Reciprocal links between portfolio and Open API pages · Objective

```html
<!-- in index.html (portfolio) -->
<a href="openapi.html">Open API Project</a>

<!-- in openapi.html -->
<a href="index.html">Back to Portfolio</a>
```
Requirement: the portfolio links **to** the Open API page **and** the Open API page links **back**. Both directions are required. Check the `href`s resolve to the correct files in the repo.

**Mentor note:** The link-back from `openapi.html` is the one most often missing — students add the outbound link from the portfolio and forget the return trip.

### Styling and layout · Subjective

- Correct answers apply CSS from the page's **own** stylesheet (separate from the portfolio's), producing a readable, intentionally laid-out page for the fetched data.
- The rendered API data should be presented cleanly (lists, cards, or a table) rather than dumped as raw JSON.
- A weak answer leaves default unstyled HTML or shows `[object Object]` / stringified JSON with no formatting.
