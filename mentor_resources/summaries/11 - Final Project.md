# Week 11 — Final Project

**Learning objective:** Demonstrate front-end proficiency by deploying a professional portfolio and a dynamic, API-driven web application, documented through a video presentation that explains the technical challenges and functionality.

## Key concepts taught

- **No new content this week.** The session is a celebratory recap of the full 11-week arc plus dedicated project work time. The slides frame the course as three phases: the language (JS), the browser (HTML/CSS/DOM/events), and the internet (Fetch/APIs/async).
- **Portfolio project (capstone 1)** — a deployed `index.html` with About, Experience, Skills, Projects, and "Leave a Message" sections; a dynamic footer copyright year; skills rendered from a JS array via a loop; a message form that validates, displays, and removes messages; and GitHub repos fetched from the API and displayed.
- **Open API project (capstone 2)** — a separate `openapi.html` (with its own CSS/JS files) making **two distinct GET requests to two different endpoints**, with navigation between the two data views, error handling for failed fetches, and reciprocal links to/from the portfolio.
- **Professional workflow** — Git version control, GitHub hosting, merging all open PRs into `main` before submission, and working from the two published rubrics as literal checklists.
- **Talking about code** — recording a 3–5 minute demo video is treated as an interview skill, not just a deliverable.
- No Odin/Scrimba track split and no AI Learning Prompts this week — students are consolidating and finishing prior work.

## Brief overview of the assignment

There are **no numbered questions** this week. The assignment is the submission and demo process for two projects students have been building since roughly Week 5. Steps:

1. **Finish the code** — complete both the portfolio and Open API pages against their rubrics ([Portfolio Rubric](https://github.com/Code-the-Dream-School/intro-to-programming-2026/wiki/Portfolio-Rubric), [Open API Rubric](https://github.com/Code-the-Dream-School/intro-to-programming-2026/wiki/Open-API-Rubric)).
2. **Merge your work** — confirm all open pull requests are merged into `main` before submitting.
3. **Submit the link** — paste the final project repository URL (`https://github.com/yourUsername/yourRepositoryName`) into the project link field.
4. **Record and upload a 3–5 min demo video** — scroll through the portfolio, demonstrate the message form (add + edit/delete an entry), switch to the Open API page, show both endpoints loading with navigation between them, switch back, then reflect on what was most challenging and most enjoyable. Recorded via Zoom, a native screen recorder, or Loom; uploaded to YouTube as **Unlisted**.
5. **Pass the course assessment** (link sent via Slack at the start of the week) to graduate.

There are no explicit stretch goals; the rubrics themselves define the ceiling. The Git task is the PR-merge-into-`main` step, the culmination of the branching/PR workflow introduced in Weeks 2–6.

## Likely trouble spots

- **Only one fetch on the Open API page.** The single most common gap: students build one working GET request but not the required **two distinct endpoints**, or they hit two endpoints but never build the navigation to switch between the resulting views. Verify both endpoints render before signing off.
- **Missing/broken navigation between the two Open API views** — the two data displays exist but there is no way for the user to toggle between them, which the rubric explicitly requires.
- **No error handling** on the fetch calls — students commonly skip the "show a message if the fetch fails" requirement because it never triggers during their happy-path testing.
- **Unmerged PRs at submission time** — the repo `main` doesn't reflect the finished work because branches were left open. This breaks graders and demos. Flag the merge step early; don't let students leave it to the last minute.
- **Reciprocal links** — portfolio links out to the Open API page but the Open API page has no link back (or vice versa). Easy to miss, explicitly in the rubric.
- **Dynamic-vs-hardcoded requirements** — the footer year and the skills list must be generated by JavaScript (a loop over an array), not hardcoded in HTML. Students who hardcode will fail those rubric lines even though the page "looks right."
- **Message form partial completion** — form submits and displays but has no remove/delete button, or doesn't validate input.
- **Demo video logistics** — uploading as **Public** instead of Unlisted, forgetting to submit the video link, exceeding/undershooting the 3–5 min window, or freezing on the "talk about your code" reflection. Reassure: it's a walkthrough, not a performance.
- **Anxiety and "I don't fully understand everything" feelings** — normal at this stage; the slides call this out. Be generous with encouragement and steer stuck students into breakout rooms during the 25–30 min work session.
